## 实际操作

1. 在 `h3_candidates` 中为每个实际审过的机会登记 `opportunity_id`、`task_type`、`trigger_input`、`decision` 和一句决定性的 `reason`。准入 `admit` 还要给 `user_action`（谁做什么，风险是什么）、`remaining_choice`（守住硬约束后仍可裁决的内容）和可回源的 `source_anchor`（`path`、`start_line`、`end_line`、`excerpt`）。`task_plan[].opportunity_id` 只引用同题型准入候选。待核或换位写明具体缺口；如果在终稿阶段才暴露缺口，将该稿存入候选 `reviewed_prompt`，运行 `h3_selection.py` 记录摘要和裁决时间。补证沿用同一 ID，新机会使用新 ID；每次判断有变化就保存，保留候选全表。

   15125（通过）：同一套装同时贡献套装与成分类目，经理点击矩阵要核对提升倍数、样本量和背后的订单集合。即使已避免重复累计，套装订单是否纳入成分对的有效样本，仍会改变可核对的集合。15101（废弃）：订单文件缺渠道列，整批等补齐已经能保证订单查询不混批。正文确实让用户读客户单表，但没有交代等待期间谁依赖合格客户文件完成什么工作。把“单表可以读”推成“必须提前可读”就多加了业务假设。这两段是依据原题的本地判读。
2. 定稿后做独立推演，输入仅含最终正文、基线及需要核实的源码。首轮先写出自己的案例和结论，再揭开原设计卡对照。有独立上下文时只传这些输入；同一上下文已见设计卡时如实按反向审查记录，避免声称完成盲审。禁止先把设计卡结果拷入复核表再找摘录。
3. 固定一个对象、一组输入和一个观察时点。用 `trigger` 写事件顺序，`correctness_test` 写这笔输入与核对操作，`outcome_a/b` 写该观察下的具体结果或控制责任。用 `invariant` 检查两支均满足全文约束。先写一个满足全文的最简单做法。再查它牺牲的用途或承担的责任，逐字核实对应观察。不合规做法造成的错误另记。该代价被需求明确接受时不能写成缺陷。
4. 在 `final_prompt_review.H3.case_review` 填以下内容。脚本检验字段及原文绑定。生成者负责验证推演、权限和消费者真实存在；把同一个依据换两种说法仍应退回。两条方案可以援引同一句业务事实。

| 字段 | 应填写的内容 |
|---|---|
| `h3_rule_version`、`decision_unit`、`decision_stage` | 新批次填写整数 3、决定所作用的对象及阶段 |
| `risk_excerpt` | 最终题面中说明风险、需求冲突或下游受影响操作的一段连续原文 |
| `observation` | 逐字摘录终稿中用户实际会做的操作或读取的结果。`correctness_test` 将这个观察落到同一时点和输入；若关键观察只能由评审人补造，转待核 |
| `basis_a`、`basis_b` | 各自保护的业务目的或保证正确性的责任；用全文核实各自的代价、授权与适用条件 |
| `naive_result` | 忽略约束直接计算或写入会出现的错误 |
| `simplest_compliant_solution` | 单独推演能够满足全文的最简单做法，包括验收条件 |
| `remaining_cost` | 在上述做法下，谁在哪次实际操作中失去什么能力，或承担哪项原文支持的正确性责任 |
| `path`、`decisive_reason` | `business` 或 `engineering`；一句写明剔除自加假设后仍成立的决定性依据 |
| `failure_window`、`responsibility_a`、`responsibility_b` | 工程路径填写同一次竞争或失败窗口，写清两种方案分别由谁防止何种过期写入、错误可见或不可恢复结果。`option_analysis.observable_result` 比较该窗口内的观察，两条方案可以收敛到同一成功值 |

5. 从推演中删掉复核人自行增加的等待时限、提前下载、抢占、补偿或再次领取步骤，再逐字指出哪个用户操作仍然会受影响。凡是任意一个幂等任务都可以套用的“等待或重复计算”“立即拒绝或以后重试”，只有正文或基线为该观察窗口提供实际业务用途时才准入。基线核实的关键用途要自然写进终稿。
6. 两支均有正文依据且观察能区分其影响，记 `supported`。分歧合理但要借助题外假设，记 `needs_evidence`，回到源码及用户场景；同轴已锁死、第二支违反硬约束，记 `unsupported`，更换冲突轴或题位。后两类停在正式写表之前。复核措辞有歧义时保留歧义，不把低置信判断包装成平台规则。
7. 在新 topic map 写 `h3_rule_version: 3`、`h3_selection_version: 1` 和 `final_review_version: 2`，沿用 `difficulty_contract_version: 3`。按原流程将同一终稿复核存入 task_plan 与 `final-prompt-reviews/<任务目录名>.json`。样稿、候选预检、单题写表和批量写表都检查新案例。交接读取本次生成清单记录的案例复核范围；已冻结的历史题按原凭证解释。

`h3-decisions.json` 按真实记录时间保存选题与终稿版本，相同输入重复执行沿用原记录。已交接题中 H3 不成立比例的分子为已交接且平台明确判 H3 不成立的题数，分母为已交接且平台明确判 H3 成立或不成立的题数。`h3_outcomes.py` 用回执账号、提交 ID、会话、基线快照、题面 SHA 和提交时间对齐；免审或跳过、人工改判、待审、详情缺失及无法绑定的记录各自列出。分母为零时比例留空。离线时传 `--details <JSON>`，文件为 `[{"account":"账号","detail":单条平台原始详情}]`。核对历史时仅列出无冻结记录的批次。按项目及题型复查准入和待核退出；抽读待核、换位的原文以发现误拦，平台未审的候选没有平台标签。

从样稿 `records` 或正式候选数组导出一次独立复核输入。把命令输出与基线源码交给复核上下文，先保存判断，再打开设计卡。输入包仅含 `prompt`、`prompt_sha256` 和 `base_commit`。

```bash
python3 <skill>/scripts/project_review.py --candidates-file <候选JSON> --topic-map <题位图JSON> --folder <任务目录名>
```

## 匿名试判中的分歧

对两个不同的小组只出示匿名历史原题，以是否准入和平台的 H3 实判做对照。第一组采用“同一输入能否推出两种结果或时序责任”的初稿判据，8 条中 3 条一致。第二组加入业务依据和待核处理，6 条废弃中 5 条被拦，4 条实判通过中 3 条获准入。两组样本不同，不能据此估算规则改进幅度或新批次通过率。

第二组漏放了 11378。读者在推演中补上了“两份候选都通过评审且协议匹配”，原文只说两者都通过参数格式校验且协议范围不同。复核应区分可以自由设定的测试数值与需要正文或源码授权的业务资格。13742 是相反的分歧：平台接受“沿用客户端限制或采用连接器默认退避”，读者却推演到二者可能约束不同字段，因而待核。此类题回源核对两条策略是否作用于同一次调用的同一项限制，核实后可以准入。

随后将余下 52 条有明确 H3 标签的原题分给两个独立上下文匿名复读。连同第二组共 62 条，准入了 15 条实判正例中的 13 条，47 条废弃中的 31 条被挡住，16 条仍被误放。第一组另有 8 条，合计覆盖所有 70 条有明确目标标签的样本。误放中常见的是评审临时引入“等首份缓存还是重复计算”“要不要提前开放下载”“谁应当重试”。6166 的原目标是避免不同参数误用缓存，1934 的原目标则明确包含空键并发填充、停用后的旧填充、到期及重启边界。两题都能想象等待或并算，只有沿各自原文追到特定故障才能判断该工程责任是否关键。基于这次回放，正式规则增加 `observation` 原文绑定及第 5 步的删假设检查。该最后修订尚待新批次前瞻验证。
