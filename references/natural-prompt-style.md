# 自然提示词校准

目标是让最终题面读起来像业务人员提出的一个完整需求，而不是多段质量闸门的拼接。

## 结构

默认落成一个连贯段落。需求确实跨多个业务阶段时可以自然分段，但每段都要继续讲同一件事；
禁止采用“第一段写主体能力，第二段集中补另一个模块、并发、恢复和回查”的验收拼装结构。
无论怎样分段，正文都必须形成连续因果：

- 从当前行为、真实问题、能力缺口或失败后果起句。
- 在同一段叙述里带出输入数据、加工过程、输出产物和受影响的第二模块。
- 将历史、并发、恢复、冲突和设计取舍放在它们实际影响的数据链位置，不集中堆到末尾。
- 最后写用户可执行的操作、可观察结果和必要验收场景。

`domain_chain`、H1/H2/H3 摘录和 review contract 可以从成稿中提取，但内部设计卡必须先于题面完成。
任何门禁失败都通过重写段落或整篇解决，禁止在文末追加固定条件句。

## 正向参考

以下题面来自真实生产校准，只参考叙述方式，不复制业务内容或句子骨架。

### 分层抽检

> 只复核高分票据会漏估低分异常。请增加分层随机抽检，绑定训练版本的待标注全集，各分层抽取数量可设，保存每票入选概率与抽样依据。人工结论汇入抽检后，按入选概率校正总体混淆矩阵和异常率，未结案或空抽分层明确提示无法估计，不把未结案当正常。结论更正触发重算，旧结果及其依据仍可回看，重试不重复累计。结案与重算并发时只发布对应同一批结论的完整结果，失败后恢复沿用原抽样。页面可发起抽检、填写结论、查看进度和下载明细。用可枚举小总体核对校正估计，覆盖更正与重算竞争。

### 班级归并

> 班级改名和合班后，日报仍用旧代码，汇总把同一归属拆开。请增加按日期生效的归并方案，支持连续改名，拒绝环路及同日多归属。每个原班级日事实只归入一个最终班级，同日同授课方式的事实数据先聚合人次再计算表达式，方式冲突报出来源。方案从草稿到发布，发布中断可续跑，重试不重复合计。发布与事实更正并发时，试算只采用发布前或发布后的完整归属和事实。历史快照及导出保留原依据，新试算冻结归并链并可独立复算。页面可编辑生效区间、预览冲突和发布。

## 反模式

- 开头只写“新增读取……的能力”，没有说明现状和为什么需要。
- 先写成普通列表或状态修改，随后追加并发、恢复和第二模块条件。
- 第一段写业务主体，空一行后用“另一个业务模块”“配套入口”“跨模块链路”等模板补条件。
- 同一批题反复出现“另一个业务入口必须……”“同一份……必须……”“形成……台账”等固定骨架。
- 用“由你选择”“全量或增量均可”代替真实冲突条件、两种方案代价和共同不变量。
- 为了命中领域、G16、G19 或查重而追加与主业务无关的句子。

## 字符和用词

- 自然使用中英文标点、括号、引号、下划线和运算符。字段、表名和命令直接保留原文，例如 orders_repair、source_table、amount >= 7。正文不能出现反引号、带转义的反引号或代码围栏。只读查重的归一化结果不得写回正文。网页粘贴产生的空格实体还原为空格，保留需求确实要表达的实体字符串。写入后比较 XLSX 单元格、解码后的 JSON 字段和 `prompt.txt` 原文。
- 用实际业务动作和对象，少堆“产出数据集”“处置结果回写”等空泛词组。禁用“水位”，按语义直接写“事务提交的位置”“最后一次确认的日志位置”或“截至哪条记录”。保留必要且能从源码或界面核实的术语和字段原名。

## 自检

每个最终题面至少回答：

1. 谁在什么业务场景中遇到什么问题，后果是什么？
2. 哪份数据从哪里来，经过什么加工，最终生成什么可观察产物？
3. 第二模块消费、写入或持久化了哪份同一产物？
4. 哪两个约束互相影响，遗漏任一项会出现什么坏结果？
5. 哪个真实冲突存在两条都可行的处理路径，各自代价是什么？
6. 用户在页面上能做什么，验收时能看到什么？
