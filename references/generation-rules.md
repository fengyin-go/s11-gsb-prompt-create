# 继承的难度与跨项目规则

本文件保留原 GSB 判例和防撞规则，历史“两侧满分”等判例仅作出处记录，不是 S11 运行或配额规则。涉及历史平台结论的是原数据说明，不代表已在 SOLO2 对新类型重新实测；S11 容量优先类型策略、目录和交接以 SKILL.md 为准。这里的 `<skill>` 均指本 skill，topic 和写表辅助脚本使用本地隔离副本。不得用原 A/B 运行流程。

### 领域准入先于难度与去重

写题前及最终写表前按 [domain-fit.md](domain-fit.md) 检查主要工作是否属于本批所属领域。2026-11-12 SOLO2 提交 1136（cc10002 第 20 题）已因 L2 判废：Vite 升级与子路径部署是主体，血缘/圈选只是验收页面。存在真实仓库、跨两个页面、满足困难特征或通过主题/查重脚本，都不能弥补领域不符。该准入是出题 AI 基于题面、源码和领域结果的语义判断，当前 G16/G19/主题脚本不执行这项判断，不得把其 ok 输出当作领域通过。

### 题面表达：写清需求，保留实现选择

题面描述真实问题、目标能力、边界条件及可观察结果。需要验证时，写清场景和预期结果，例如“并发争用最后一个名额时仅一份申请成功，重复申请不重复扣减”，不要追加“提供某个 verify 文件并接受指定 --case 参数”这类人为交付契约。

除用户明确要求或已有真实接口契约外，不指定新增文件名/目录、脚本入口、CLI 参数、测试框架、内部类名或实现拆分。已有路径和字段可用于准确说明问题与兼容范围，不能为了让交接脚本有命令可跑而发明接口或测试产物。

出题侧的复现、准入检查与运行后的验收/录屏方案放在证据和交接元数据中。需求检查可以描述操作、输入与预期结果；可执行命令须依据真实已有入口，功能完成后再结合实际产物补充验证。基础编译或启动检查只能证明其覆盖的事实，不能充当业务验收。写表前逐条检查末尾是否夹带与用户目标无关的工程化要求，发现即删除并同步所有题面副本及交接哈希。

1 条 G17 返修，一条都没过；这 5 条的判词要点就是下面这组「中等模板」的原型）：

| 编号 | 任务类型 | 平台结论 | 判词要点 |
|---|---|---|---|
| 3 | 功能开发 | 废弃 G16 | 新增实体的常规登记、筛选排序、校验与状态保持，无架构级设计 |
| 2 | 功能开发 | 废弃 G16 | 业务功能明确，涉及状态同步与批量部分失败等边界，但无需架构级整合或关键取舍 |
| 14 | 功能开发 | 废弃 G16 | 读懂既有模块并新增台账、校验、汇总与持久化，有多个边界约束但无架构级取舍 |
| 31 | 代码重构 | 废弃 G16 | 定位三处重复校验、合并为同一判定并保持历史行为不变，属跨调用点重构，无架构级取舍 |
| 5 | 功能开发 | 返修 G17 | 题面判定的真实难度为困难，没有体现地狱级特征 |

平台判 `困难` 看的三项特征（`2026-09-29` 原口径：普通任务类型至少要**成立两项**；
`Bugfix`（含 `Bug修复` / `bugfix` 别名）必须**三项全部成立**）：

1. **多模块整合**：需求逼着另一个业务面一起变，而不只是本模块的列表与详情保持一致。
   例如看板/概览/统计的条数跟着明细变、审批结论回写计划行、一个模块的状态决定另一个模块
   的清单、批量结果驱动台账与统计两处重算。
2. **关键设计取舍**：题面逼出一次设计判断。例如把散落的口径收成一份、规则冲突时的优先级、
   兼容既有数据、幂等保证、历史按当时口径留痕、迁移与回填。
3. **复杂技术关注点**：并发与幂等、权限与归属、事务与落库一致性、状态机跳级拦截、
   失败链路与断点续做、性能与分页、跨环境兼容。

这三项放到类型上再收紧一层（**现行口径，2026-10-01 恢复**）：`功能开发` / `代码重构` /
`依赖升级与迁移` / `功能优化` 按「三项至少两项」；`Bugfix`（含 `Bug修复` / `bugfix` 别名）
按「三项全备」——多模块整合 + 关键设计取舍 + 复杂技术关注点，缺一项不能落表。这正是
2026-09-29 那版口径；2026-09-30 一度对后两类放行，2026-10-01 已撤回（依据见上）。

**硬证据闸（2026-09-30 起，五类都适用）**：三项特征光靠弱证据撑不算数，
至少要有一项落到硬证据组。
判废 15 条（cc10016 13 条 + cc10017 2 条）时，本地词面闸门把下面这些写法都当成了困难特征，
而平台判词逐条否定过（15 条全部回到「必须拦住」——2026-09-30 那版把其中 6 条
`Bug修复` / `feature迭代` 放行了，2026-10-01 随放宽一起撤回）：

| 弱证据写法（不算困难） | 平台判词 |
|---|---|
| 本模块概览/看板/统计数字与列表一致 | #14「保持概览一致，属常规局部到跨层实现」 |
| 以后端返回为准、前端不再各自重算 | #14「无架构取舍」 |
| 单独一句历史按当时口径保留 | #3「需理解跨视图数据流并处理若干业务规则」 |
| 批量逐条回执、只跳过那一条 | #2「批量部分失败等边界」不算 |
| 把散落在几处的判断收拢成一份 | #31「跨调用点重构，无架构级取舍」 |

硬证据组只有九类，写题时必须至少命中一类，而且要落在**主诉求**上，不是末尾补一句：

1. **状态机与单向推进**：跳级/倒序拦截、只能按顺序推进、不允许回退；
2. **并发与幂等**：并发提交只生效一次、重复提交只扣一次账、反复初始化不产生重复；
3. **权限与归属**：越权拦截、只有本单位能改、跨单位拒绝、只读与职责分离；
4. **事务与落库一致性**：字段没落库、保存与读取不是同一份、驳回要清空中间态；
5. **断点续做与失败链路**：失败后从失败那一行接着走、取不到就重试而不是顶旧数据；
6. **口径版本化与重算**：口径调整后已录数据按新口径重算、历史按当时口径留档；
7. **迁移与存量回填**：存量数据按采集顺序回填、历史数据兼容；
8. **另一个业务面跟着变**：导出/审批/待办/台账/工作台真的多出一份东西，不是只改一个数字；
9. **冲突口径与优先级裁决**：冲突时以谁为准、谁优先。

**明确不合格的写法**（G16 判词点名的中等模板）：新增/登记一个实体 + 列表呈现（筛选、排序、
分组）+ 基础校验（必填、格式、范围）+ 刷新后仍在，通篇读不到上面任何一项。这类题不是把
形容词写足就能过关，必须换切入点，把跨模块后果或设计约束真正写进需求。这条对五类都生效，
`Bug修复` / `feature迭代` 不再例外。

判词里被点名**否定**过、不能当困难特征用的两件事：

- **批量部分失败不算**：「逐条回执、只跳过不通过的那一条、其余照常」这类边界，平台在
  `#2` 的判词里明确说不构成困难（与它同形状的 `#14` 也一样被判废）；
- **跨调用点收拢不算关键取舍**：「把散落在几处的同一段判断合并成一份、行为保持不变、
  不加新能力」在 `#31` 的判词里被判成中等，只有真的带架构级取舍（口径以谁为准、
  兼容既有数据、迁移回填、优先级裁决）才算。

`地狱` 另有一道坎（五类一视同仁）：只有题面
同时具备「需求高度开放或约束隐蔽 / 需要架构级判断 / 多步复杂的调试与验证 / 正确性依赖
大量边界场景」其中两项时才能标 `地狱`；只到 `困难` 却标了 `地狱`
会被平台按 G17 打回（改标 `困难` 重提即可，但要多占一次平台往返）。默认按 `困难` 出，
没有把握就不要标 `地狱`。

#### 多模块纪律：每题都必须落在 ≥2 个功能模块上（2026-10-01 起硬性出题纪律）

「单一功能」是 G16 / G19 判词里出现最多的短板，也是这次 654 条回执里最集中的规律：
被判废的题面反复出现「单一…功能」「属常规局部到跨层实现」「在既有 X 模块内实现」
「无架构取舍」「无需架构级重设计」这类判词。

- 出题时把**一个需求要牵动的两个业务面**写进主诉求：本模块之外真的多出一份东西
  （导出 / 审批 / 待办 / 台账 / 工作台 / 初始化数据跟着变），而不是本模块的列表与详情
  互相对齐、也不是「本模块概览的条数与列表一致」。
- 只有 `概览 / 看板 / 统计` 与 `列表` 数字对齐撑起来的「多模块整合」是**弱证据**，
  平台在 #14 判词里点名否定过（「保持概览一致，属常规局部到跨层实现」）；
  脚本会给 `弱证据` 提示，`--strict` 下当不合格。
- 脚本在每条结果里输出 `multi_module` 与 `multi_module_signals`：`false` 表示这条题面
  读不出第二个业务面。**写表时把 `multi_module: false` 的条数记进生成清单
  （`multi_module_missing_count`），这些条目必须重写出跨模块后果，不能用备注绕过。**

#### G19：迭代 / 修复题的三项中等特征（2026-10-01 平台新规则）

平台对 `feature迭代` / `Bug修复` 是**两层**判：先看「中等」是否成立（G19），再看「困难」
是否成立（G16）。G19 的「中等」要同时成立三项，缺一项就作废、不可返修：

1. **调用与数据流理解**：要顺着既有代码的调用链或数据流定位改动点，而不是在单页里加一段。
2. **实现决策**：题面要留出影响结果对错的实现选择（以谁为准、口径怎么统一、兼容既有数据、
   迁移回填、优先级裁决…）。平台判词对「做法基本给定」「做法被写死」是直接判废的。
3. **边界条件与约束**：并发 / 幂等 / 权限归属 / 事务落库 / 状态推进 / 断点续做 / 极值…
   至少要有几个**非平凡**约束；「空态提示 + 导出失败重试」这种逐条列明的做法不算。

「实现决策」是语义判断，词面无法可靠复现，所以脚本只给近似读数：
`g19_applies` / `g19_ok` / `g19_hit_features` / `g19_missing_features` / `g19_evidence`，
缺项时进 `hints` 提示，`--strict` 下才当不合格。**写题时就按 `g19_ok: true` 去写**
（顺着既有链路找改动点 + 留一个实现决策 + 若干非平凡边界）；读不全时逐条人工复核——
确实是语义写到了而词面没读出来的，按 `难度复核` 备注留档；平台判废 #19 / #15 的形状
（「做法基本给定」「做法被写死，缺实现决策」）必须换切入点重出，不能只改措辞。
注意这个读数很保守：本轮 cc10019 的 24 条迭代 / 修复题里 23 条会被标出缺项，
它的用途是**逐条复核的名单**，不是「23 条全都要重写」。

固定命令（写表前逐条查、整批写完再全量复检，两次都必须 `ok: true`）：

```bash
python3 <skill>/scripts/check_prompt_g16.py \
  --parent "<父目录>"
# 单条候选在写表前也可以直接用同一把尺子量：
python3 <skill>/scripts/check_prompt_g16.py \
  --prompts-file "<这一条提示词的临时文件>"
# 批量自查（把 hints 也当不合格：单一功能模块 / G19 疑似不达中等 / 硬证据只在末句）：
python3 <skill>/scripts/check_prompt_g16.py \
  --parent "<父目录>" --strict
```

脚本按「五类任务类型一律至少两项（`Bugfix` 三项全备）、且至少一项是硬证据」硬判，
不再对任何类型放行（输出里 `g16_enforced: true`、`g16_exempt_count: 0`）。判据只有一份，
在 `$cc-gsb-create` 的 `scripts/gsb_difficulty.py`，本脚本直接加载它，两边不允许各抄一套
（见脚本输出里的 `judge` 字段）；G19 的「中等」词面读数与多模块读数定义在
`check_prompt_g16.py` 里（`MEDIUM_FLOOR_PATTERNS` / `MULTI_MODULE_EXTRA_PATTERNS`），
只做提示与 `--strict` 自查，不参与 G16 硬判。它返回 `ok: true` 只说明词面上
达到对应类型的最低项数，生成方仍要按上面的特征逐条自查。被脚本拦下的条目优先换角度重出，
不许只加限定词，也不许用
`--allow-gate-failure` 硬塞；确实判断这条题能到 `困难` 时，把要求成立的特征逐项写进工作簿
备注并以「`难度复核: `」开头留档（普通类型写两项、`Bugfix` 写三项，G19 的三项中等
特征名也算数）。脚本命中但备注复核过的条目只留痕、不拦
（`justified` 字段里能查到是哪几条走了这条路）。

默认（不带 `--strict`）硬拦 G16，以及 2026-10-07 平台真实回执确认的两种 G19 高危形状：
「排序 + 分页 + 回到第一页/空态说明」和「空态提示 + 重新登记入口 + 导出失败重试」。
`--strict` 另把脚本的 `hints` 也算不合格，用来批量挑出三类擦边题面：单一功能模块、
G19 疑似不达中等、硬证据只出现在末句（「主诉求还是列表一致、末尾补一句断线重试」）。
**GSB 批次建议在整批写完时再跑一遍 `--strict` 并记录 `strict_only_violation_count`**：
命中的条目要么重写，要么按上面的口径写 `难度复核` 备注留档，不允许静默带过。

#### 平台回执负向硬闸（2026-10-08 起）

除正向困难判据外，`check_prompt_g16.py` 还增加了只做降级、不做升级的平台负向硬闸。
这些形状在 `gonghao` 2026-10-07 的真实回执里即使能命中若干硬证据词，平台仍判中等：

- **跨调用点收拢**：两条/几条路径或几处判定「收拢/合并/抽成一份共用实现」，
  除非另有一个真正需要状态、权限、事务、迁移或冲突裁决的切入点。
- **单业务域新建台账**：新建台账 + 重算/回填/去重，但只依赖同一台账的列表、详情、
  概览一致；必须再引入审批、导出、权限归属、跨单位、工作台等第二个真实业务面。
- **示例数据铺底**：示例数据初始化/复位 + 备份/重试/多视图一致，但没有真实迁移、
  数据版本、权限、事务或状态链。

命中负向硬闸的条目输出 `platform_learned_blocks` / `platform_learned_reasons`，
并且**不能用「难度复核」备注放行**。对应真实漏网样本固定在
`tests/fixtures/platform-g16-g19-rejections-20261007.json`。

标定语料在 `tests/fixtures/g16-corpus.json`：cc10016 / cc10017 的 15 条判废 + 33 条质检通过，
外加 2026-10-01 补进的 4 条真实回执（1 条废弃 G16、2 条废弃 G19、1 条废弃 G18）。
`python3 -m pytest tests/test_check_prompt_g16.py -q` 的断言口径：15 条废弃必须全拦、
通过的那 33 条里只允许闸门上线前就存在的 13 条过拦、G19 两条要被
`g19_ok: false` 命中（`--strict` 下拦）、G18 那条与难度闸无关不参与难度断言。

### 5.1 跨项目全局防撞（2026-09-28 起跨目录硬闸）

这个闸门解决的是“单个项目内部已经不复读，但多个项目之间仍在套同一句骨架”：
`wx10001` 与 `wx10002` 的旧题面里，概览视图、批量作业、状态流转、规则阈值、导入导出、
权限归属、边界空态、列表筛选和持久一致性九组题都复用了同一开头、同一动作顺序和同一异常约束，
只把业务对象、页面名和字段名换掉。平台会把这判成跨项目相似并废弃，普通同仓库查重看不见。

执行口径：

- 出题前先同步当前 SOLO-QA 账号的平台题面快照。快照默认写到
  `data/platform-prompt-corpus.json`（该目录机器本地忽略，不提交），`update` 的跨项目
  检查会自动加载它，并用比提交侧更严的口径比较：相似度不低于 `13%`，或最长公共
  汉字片段达到 `30` 字即失败。
- 平台“雷同题库”已确认按关键词拒收的 `待办清单` 作为硬黑名单命中即拒写；平台明确
  说明该类换措辞无效，必须换真实业务场景。
- 跨项目范围以 `<父目录>/gsb-cross-project.json` 指向的注册表为准，不再要求所有批次在同一个
  父目录下。注册表里的每个工作簿路径都可以在不同目录树；注册表路径默认是
  `scripts/../data/cross-project-registry.json`，可用配置或 `GSB_CROSS_PROJECT_REGISTRY` 覆盖。
- `batch_prompt_workbook.py update` 检测到批次目录存在 `gsb-cross-project.json` 后，会自动读取
  注册表、加跨进程锁、执行跨项目检查；写表成功后把当前工作簿的路径、SHA-256、题面数量和更新时间
  原子写回注册表。注册表缺失、哈希不一致、题面数量不一致或覆盖不完整时直接拒写。
- 注册表模式下默认 `--require-coverage`：注册表里的工作簿必须存在且哈希匹配，当前批次至少要有
  1 条有题面的历史批次。零 peer 不是“通过”，只有显式 `--bootstrap-no-history` 才能放行首次批次；
  放行结果会写进生成清单。
- 出题前先扫描当前工作簿与全部已登记批次；每写一条题面前，`update` 内部会自动再查一次；
  整批写完后再全量复检一次。三次都必须在写表之前或写表后立即通过，不能等到投递后才发现。
- 命中近邻后，只改业务名词、页面名、同义词或标点不算重出。必须改至少两项：
  首屏形态（独立页 / 内嵌面板 / 日历 / 矩阵 / 时间轴 / 队列）、主交互对象、
  动作顺序、前后状态关系、异常反馈机制；同一 `任务类型 + 需求模式` 的解法形态不能照搬。
- `check_prompt_dedup.py` 只覆盖当前批次和历史记录，不能代替这个跨项目闸；
  `check_repo_theme.py` 只覆盖当前仓库的 topic × 模式，也不能代替。

固定命令：

```bash
# 出题前先同步平台历史题面语料；无缓存或需要最新结论时加 --refresh
python3 <skill>/scripts/sync_platform_prompt_corpus.py

# 首次登记：把不同目录树下的历史批次登记进注册表；先 dry-run，再 --register；旧 GSB 工作簿需额外传 --workbook solo-create-prompts.xlsx
python3 <skill>/scripts/register_cross_project_batches.py \
  --scan-root "<历史批次根目录 A>" \
  --scan-root "<历史批次根目录 B>" \
  --registry "<注册表路径>" --max-depth 8
python3 <skill>/scripts/register_cross_project_batches.py \
  --scan-root "<历史批次根目录 A>" \
  --scan-root "<历史批次根目录 B>" \
  --registry "<注册表路径>" --max-depth 8 --register --write-batch-config

# 出题前：按注册表扫描当前批次已有题面，找出与全部历史批次最接近的记录
python3 <skill>/scripts/check_cross_project_prompts.py \
  --batch-dir "<父目录>" --registry "<注册表路径>" \
  --require-registry --require-coverage --min-peer-batches 1 \
  --require-platform-corpus

# 写表前：逐条检查最终提示词；失败就换解法形态重出，不能直接 update 硬写
# 有 gsb-cross-project.json 时，batch_prompt_workbook.py update 已自动执行这一步；
# 下面命令用于单独预检或排错。
python3 <skill>/scripts/check_cross_project_prompts.py \
  --batch-dir "<父目录>" --registry "<注册表路径>" \
  --require-registry --require-coverage --min-peer-batches 1 \
  --prompt "<最终提示词>" --task-type "<任务类型>" --source-folder "<子文件夹名称>"

# 整批完成后：按工作簿全量复检
python3 <skill>/scripts/check_cross_project_prompts.py \
  --batch-dir "<父目录>" --registry "<注册表路径>" \
  --require-registry --require-coverage --min-peer-batches 1
```

`gsb-cross-project.json` 由建仓脚本在非 dry-run 建仓时自动写入；已有批次可手工补一份，或由
建仓脚本后续重跑时补写。首次批次确实没有任何历史时，把配置里的 `bootstrap_no_history` 临时设为
`true`，跑完首次建仓/生成后立即改回 `false`，并在生成清单里保留这次 bootstrap 记录。
`--allow-gate-failure` 只放开同仓库主题、难度和批内去重，不能绕过跨项目注册表硬闸。

脚本默认硬拦（先限定为同一任务类型且需求模式有交集，避免把不同模式只共享行业词的题误伤）：

- 字符三元组重合率 `> 20%`；
- 字符二元组余弦近似度 `> 35%`；
- 规范化开头公共前缀 `>= 12` 字；
- 两条题共享 `> 2` 个八字中文片段，或出现 `>= 20` 字连续中文片段；
- 解法形态重合并伴随三个以上业务能力点重合，或字符重合率超过 `16%`；
- 若任务类型或需求模式不相交，只在文字重合率 `> 60%`、语义近似度 `> 70%`，
  或连续中文片段达到 `40` 字时按极端克隆拦截。

输出必须带 `cross_project_ok`、`coverage_ok`、`registry_used`、`registry_path`、
`registry_batch_count`、`cross_project_violation_count`、
`cross_project_max_text_overlap`、`cross_project_max_semantic_similarity`、
`cross_project_max_common_fragment_length`、`cross_project_peer_batches`、`coverage_issues`、
`platform_guard_ok`、`platform_corpus_used`、`platform_corpus_path`、
`platform_dedup_ok`、`platform_dedup_violation_count`、`platform_dedup_max_similarity`、
`platform_dedup_max_common_fragment_length`、`platform_dedup_nearest`、
`platform_forbidden_topic_ok`、`platform_forbidden_topic_violations` 和最近邻明细。
任一失败时不得写工作簿；按最近邻逐条写出“入口形态、动作顺序、状态关系、异常反馈”四个差异点后重出。
