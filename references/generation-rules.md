# 继承的难度与跨项目规则

本文件保留原 GSB 判例和防撞规则，历史“两侧满分”等判例仅作出处记录，不是 S11 运行或配额规则。涉及历史平台结论的是原数据说明，不代表已在 SOLO2 对新类型重新实测；S11 容量优先类型策略、目录和交接以 SKILL.md 为准。这里的 `<skill>` 均指本 skill，topic 和写表辅助脚本使用本地隔离副本。不得用原 A/B 运行流程。

### 领域准入先于难度与去重

写题前及最终写表前按 [domain-fit.md](domain-fit.md) 检查主要工作是否属于本批所属领域。2026-11-12 SOLO2 提交 1136（cc10002 第 20 题）已因 L2 判废：Vite 升级与子路径部署是主体，血缘/圈选只是验收页面。2026-11-15 `dfzr10006` 又有 5 条因 `DOMAIN_MISMATCH` 停在 `PENDING_FIX`：路由灰度、限流状态机、网关部署、权限配额和发布流水线都被平台认定为通用服务/部署逻辑，数据工程仓库身份不能改变主任务属性。

存在真实仓库、跨两个页面、满足困难特征或通过主题/查重脚本，都不能弥补领域不符。v2 领域闸要求每个题位冻结 `domain_chain`（领域输入、处理、输出、可观察结果）、前置 `prompt_main_request`、反事实通用任务说明和至少两条带行号连续原文的 `domain_anchors`。最终题面必须逐字保留整条链路；语义判断仍由出题 AI 完成，G16/G19/主题脚本的 ok 不能替代它，脚本通过也不能替代逐题阅读。

### 题面表达：写清需求，保留实现选择

起草前先完成 SKILL.md 的内部设计卡，确认领域主体、真实题型、H1/H2 数据链路及 H3
冲突与方案代价。起草时直接落实这些规则，而不是生成一批简单题后靠检查逐项补尾句。
关键取舍用具体业务条件和结果边界表达，不写“由你权衡优先项”“由设计者决定”
“请自行选择”等显式委托，也不将内部参考方案塞进用户题面。

输出样稿之前同样执行 SKILL.md 的“样稿也须先准入”：运行 `check_prompt_preview.py`，
领域和 H1/H2/H3 不得留到用户确认文风后再补。简单除法配“全量或增量自行选择”不是充分 H3；
参数转发和静态路由修复也不会因服务于导出而自动成为数据工程。真实取舍所需的条件、
源码锚点、逐方案成本分析及数据链路影响按 `difficulty-hardening.md` 填写，不能靠开放短语过关。

题面直接写要实现的业务需求，不描述“提出这项需求”的过程。删除“本需求需要……”“本次任务要……”“这次我需要……”“请你帮我……”等需求自指、时间指代或第一人称请求外壳，按题型自然写目标行为、业务边界和可观察结果，不要求以“请”开头。功能开发从能力缺口或新增目标切入，Bugfix 从真实故障现象切入，功能优化从已有链路及改进目标切入；重构和迁移分别写清不变行为、版本兼容目标。不统一开场模板，“请”可用但不是类型语义或领域准入条件。正常业务语义中的时间描述可以保留，例如“本次结算周期只处理已确认记录”，因为它限定业务批次而不是复述出题请求。写表闸会用 `prompt_style.py` 拦截明显的元叙述，最终题面仍要人工确认通篇是在讲业务，不是在讲“这次题目”。

每批先读取仓库外的 `prompt-opportunities/<project_id>.json`，机会地图只用于复核业务故事、
数据链、冲突轴和源码锚点。最终题面必须一次写成完整业务叙述，再从正文提取领域链与
H1/H2/H3 证据。门禁失败时重写段落或整篇，不允许在文末追加“另一个业务入口必须……”
“同一份……必须……”等模板条件。`check_prompt_naturalness.py` 与
[natural-prompt-style.md](natural-prompt-style.md) 是独立质量闸。

题面不得包含模型上下文隔离声明或信息来源限制，不论在开头、末尾、标题、附注还是交接追加段，也不论是否使用同义表达。业务数据的权限、来源口径和时间范围不属于此类模型上下文限制。历史去重代码为兼容旧批次保留的识别文字仅供历史归一化，不是题面模板，不得作为生成或交接输入。

先写能让项目使用者理解的需求，再从自然题面提取领域契约中的输入、处理、输出和观察结果片段；这些片段仍须逐字对应题面，但不能为了填字段而拼成套话。`prompt_main_request` 可以是一段自然开场，而不是强制一条长句。Bugfix 恢复既有能力，不附加此前不存在的计算或产物；功能优化改善既有链路，不偷换成首次开发。不得仅为凑难度强行扩大需求范围。

通读时，每条关联要求应能回答具体是哪个模块、使用哪些数据、用户会看到什么变化；每条取舍应对应真实存在的冲突。未指明对象的“另一个入口”、不明用途的状态和凭空出现的两版来源不是合格业务要求。硬闸拦截已知空泛拼接句，其他同类问题仍须逐题人工复核；不满足真实难度时换题，不用通用尾句补齐。

题面描述真实问题、目标能力、边界条件及可观察结果。需要验证时，写清场景和预期结果，例如“并发争用最后一个名额时仅一份申请成功，重复申请不重复扣减”，不要追加“提供某个 verify 文件并接受指定 --case 参数”这类人为交付契约。

### 任务类型语义

题型语义必须出现在最终题面的第一个主动作里，不能先写通用数据读取、计算或列表调整，再在
后句补“修复”“优化”或“新增”。`domain_fit.main_task`、`prompt_main_request` 和最终题面
必须表达同一件事；工作簿题型、目录 slug、`task_plan.task_type`、`family` 必须一致。

- 功能开发要有能力缺失基线（当前尚未形成、缺少、没有）和新增后的可观察产物。只把现有
  数据重新读取、计算或展示，不因出现“请”而自动成为功能开发。
- Bugfix 要有真实缺陷、错误现象或失败后果，修复后恢复既有可观察行为。正常能力建设不能
  通过添加“修复”前缀过关，缺陷证据还要能回查基准源码。
- 功能优化必须针对现有/已有/当前能力，并在开头写清性能、稳定性、去重、失败恢复等改进
  目标；首次实现或新增数据能力不能标成功能优化。
- 代码重构必须声明既有行为、输入输出或口径保持不变；只收拢调用点仍要满足重构的原有约束。
- 依赖升级与迁移必须有真实版本、依赖、兼容、存量、回滚或迁移目标。

`check_prompt_type_intent.py` 在题位、写表和交接三处执行该闸；命中后重写业务意图，不要只改
开头动词或补一句类型词。

领域主请求必须先于权限、路由、灰度、缓存、发布和 UI 支撑要求出现，并让人读懂真实数据输入、处理和结果；不限定句式，不统一要求新增数据集。Bugfix 可以先交代导出错误、筛选失效等有证据的业务故障，再说明应恢复的数据结果。不得先写一大段通用服务逻辑，再在末句补“数据结果保持一致”。

除用户明确要求或已有真实接口契约外，不指定新增文件名/目录、脚本入口、CLI 参数、测试框架、内部类名或实现拆分。已有路径和字段可用于准确说明问题与兼容范围，不能为了让交接脚本有命令可跑而发明接口或测试产物。

出题侧的复现、准入检查与运行后的验收/录屏方案放在证据和交接元数据中。需求检查可以描述操作、输入与预期结果；可执行命令须依据真实已有入口，功能完成后再结合实际产物补充验证。基础编译或启动检查只能证明其覆盖的事实，不能充当业务验收。写表前逐条检查末尾是否夹带与用户目标无关的工程化要求，发现即删除并同步所有题面副本及交接哈希。

### 平台验收准备度

2026-11-15 `dfzr10007` 39 条首次提交中，13 条难度废弃、8 条待返修。待返修不是同类问题：

- 05/12：把缺测试依赖、`pkill` 或退出码 144 等环境噪声当成模型扣分；
- 19/22：过程句压缩成电报体；
- 25/36：只写测试通过总数，没有落到业务行为；
- 28/31：轨迹读取跨会话答案笔记。

因此最终交接除了 requirements，还必须填写 [review-readiness.md](review-readiness.md) 的
`review_contract`。出题侧要提前说清每个需求的可观察行为、测试行为映射、关键约束句和环境
噪声排除项；不要求 `context_isolation`，不得向最终题面加入上下文或信息来源限制。`prepare_handoff.py` 会拒绝业务契约缺项，
并把契约冻结到 `review-contract.json`。

平台判 `困难` 看的三项特征（`2026-09-29` 原口径：普通任务类型至少要**成立两项**；
`Bugfix`（含 `Bug修复` / `bugfix` 别名）必须**三项全部成立**）：

1. **多模块整合**：需求逼着另一个业务面一起变，而不只是本模块的列表与详情保持一致。
   例如看板/概览/统计的条数跟着明细变、审批结论回写计划行、一个模块的状态决定另一个模块
   的清单、批量结果驱动台账与统计两处重算。
2. **关键设计取舍**：题面逼出一次设计判断。例如把散落的口径收成一份、规则冲突时的优先级、
   兼容既有数据、幂等保证、历史按当时口径留痕、迁移与回填。
3. **复杂技术关注点**：并发与幂等、权限与归属、事务与落库一致性、状态机跳级拦截、
   失败链路与断点续做、性能与分页、跨环境兼容。

这三项放到类型上再收紧一层（**现行口径，2026-10-01 恢复**）：`功能开发` / `代码重构` /
`依赖升级与迁移` / `功能优化` 按「三项至少两项」；`Bugfix`（含 `Bug修复` / `bugfix` 别名）
按「三项全备」——多模块整合 + 关键设计取舍 + 复杂技术关注点，缺一项不能落表。这正是
2026-09-29 那版口径；2026-09-30 一度对后两类放行，2026-10-01 已撤回（依据见上）。

**硬证据闸（2026-09-30 起，五类都适用）**：三项特征光靠弱证据撑不算数，
至少要有一项落到硬证据组。
判废 15 条（cc10016 13 条 + cc10017 2 条）时，本地词面闸门把下面这些写法都当成了困难特征，
而平台判词逐条否定过（15 条全部回到「必须拦住」——2026-09-30 那版把其中 6 条
`Bug修复` / `feature迭代` 放行了，2026-10-01 随放宽一起撤回）：

| 弱证据写法（不算困难） | 平台判词 |
|---|---|
| 本模块概览/看板/统计数字与列表一致 | #14「保持概览一致，属常规局部到跨层实现」 |
| 以后端返回为准、前端不再各自重算 | #14「无架构取舍」 |
| 单独一句历史按当时口径保留 | #3「需理解跨视图数据流并处理若干业务规则」 |
| 批量逐条回执、只跳过那一条 | #2「批量部分失败等边界」不算 |
| 把散落在几处的判断收拢成一份 | #31「跨调用点重构，无架构级取舍」 |

硬证据组只有九类，写题时必须至少命中一类，而且要落在**主诉求**上，不是末尾补一句：

1. **状态机与单向推进**：跳级/倒序拦截、只能按顺序推进、不允许回退；
2. **并发与幂等**：并发提交只生效一次、重复提交只扣一次账、反复初始化不产生重复；
3. **权限与归属**：越权拦截、只有本单位能改、跨单位拒绝、只读与职责分离；
4. **事务与落库一致性**：字段没落库、保存与读取不是同一份、驳回要清空中间态；
5. **断点续做与失败链路**：失败后从失败那一行接着走、取不到就重试而不是顶旧数据；
6. **口径版本化与重算**：口径调整后已录数据按新口径重算、历史按当时口径留档；
7. **迁移与存量回填**：存量数据按采集顺序回填、历史数据兼容；
8. **另一个业务面跟着变**：导出/审批/待办/台账/工作台真的多出一份东西，不是只改一个数字；
9. **冲突口径与优先级裁决**：冲突时以谁为准、谁优先。

**明确不合格的写法**（G16 判词点名的中等模板）：新增/登记一个实体 + 列表呈现（筛选、排序、
分组）+ 基础校验（必填、格式、范围）+ 刷新后仍在，通篇读不到上面任何一项。这类题不是把
形容词写足就能过关，必须换切入点，把跨模块后果或设计约束真正写进需求。这条对五类都生效，
`Bug修复` / `feature迭代` 不再例外。

判词里被点名**否定**过、不能当困难特征用的两件事：

- **批量部分失败不算**：「逐条回执、只跳过不通过的那一条、其余照常」这类边界，平台在
  `#2` 的判词里明确说不构成困难（与它同形状的 `#14` 也一样被判废）；
- **跨调用点收拢不算关键取舍**：「把散落在几处的同一段判断合并成一份、行为保持不变、
  不加新能力」在 `#31` 的判词里被判成中等，只有真的带架构级取舍（口径以谁为准、
  兼容既有数据、迁移回填、优先级裁决）才算。

`地狱` 另有一道坎（五类一视同仁）：只有题面
同时具备「需求高度开放或约束隐蔽 / 需要架构级判断 / 多步复杂的调试与验证 / 正确性依赖
大量边界场景」其中两项时才能标 `地狱`；只到 `困难` 却标了 `地狱`
会被平台按 G17 打回（改标 `困难` 重提即可，但要多占一次平台往返）。默认按 `困难` 出，
没有把握就不要标 `地狱`。

#### 多模块纪律：每题都必须落在 ≥2 个功能模块上（2026-10-01 起硬性出题纪律）

「单一功能」是 G16 / G19 判词里出现最多的短板，也是这次 654 条回执里最集中的规律：
被判废的题面反复出现「单一…功能」「属常规局部到跨层实现」「在既有 X 模块内实现」
「无架构取舍」「无需架构级重设计」这类判词。

- 出题时把**一个需求要牵动的两个业务面**写进主诉求：本模块之外真的多出一份东西
  （导出 / 审批 / 待办 / 台账 / 工作台 / 初始化数据跟着变），而不是本模块的列表与详情
  互相对齐、也不是「本模块概览的条数与列表一致」。
- 只有 `概览 / 看板 / 统计` 与 `列表` 数字对齐撑起来的「多模块整合」是**弱证据**，
  平台在 #14 判词里点名否定过（「保持概览一致，属常规局部到跨层实现」）；
  脚本会给 `弱证据` 提示，`--strict` 下当不合格。
- 脚本在每条结果里输出 `multi_module` 与 `multi_module_signals`：`false` 表示这条题面
  读不出第二个业务面。**写表时把 `multi_module: false` 的条数记进生成清单
  （`multi_module_missing_count`），这些条目必须重写出跨模块后果，不能用备注绕过。**

#### G19：迭代 / 修复题的三项中等特征（2026-10-01 平台新规则）

平台对 `feature迭代` / `Bug修复` 是**两层**判：先看「中等」是否成立（G19），再看「困难」
是否成立（G16）。G19 的「中等」要同时成立三项，缺一项就作废、不可返修：

1. **调用与数据流理解**：要顺着既有代码的调用链或数据流定位改动点，而不是在单页里加一段。
2. **实现决策**：题面要留出影响结果对错的实现选择（以谁为准、口径怎么统一、兼容既有数据、
   迁移回填、优先级裁决…）。平台判词对「做法基本给定」「做法被写死」是直接判废的。
3. **边界条件与约束**：并发 / 幂等 / 权限归属 / 事务落库 / 状态推进 / 断点续做 / 极值…
   至少要有几个**非平凡**约束；「空态提示 + 导出失败重试」这种逐条列明的做法不算。

「实现决策」是语义判断，词面无法可靠复现，所以脚本只给近似读数：
`g19_applies` / `g19_ok` / `g19_hit_features` / `g19_missing_features` / `g19_evidence`，
缺项时进 `hints` 提示，`--strict` 下才当不合格。**写题时就按 `g19_ok: true` 去写**
（顺着既有链路找改动点 + 留一个实现决策 + 若干非平凡边界）；读不全时逐条人工复核——
确实是语义写到了而词面没读出来的，也必须用 `difficulty_design` 的 H1/H2/H3 源码锚点和
题面摘录证明；旧的 `难度复核` 备注不再放行。平台判废 #19 / #15 的形状
（「做法基本给定」「做法被写死，缺实现决策」）必须换切入点重出，不能只改措辞。
注意这个读数很保守：本轮 cc10019 的 24 条迭代 / 修复题里 23 条会被标出缺项，
它的用途是**逐条复核的名单**，不是「23 条全都要重写」。

固定命令（写表前逐条查、整批写完再全量复检，两次都必须 `ok: true`）：

```bash

# 单条候选在写表前也可以直接用同一把尺子量：
```

`--strict` 另把脚本的 `hints` 也算不合格，用来批量挑出三类擦边题面：单一功能模块、

#### 结构化困难契约（2026-11-15 起硬闸）

2026-11-15 `dfzr10007` 的 13 条题面使用同一条通用 `难度复核` 备注通过了旧闸，提交后
被平台按 P4/P5 判废。逐题情况与改造方向固定在
[difficulty-hardening.md](difficulty-hardening.md)。现行规则：

- 新 topic map 必须有 `difficulty_contract_version: 3`。
- 每个 `task_plan[]` 必须有 `difficulty_design`，不能用备注或最终题面倒填。
- H1 `reasoning_challenge` 至少两条不同类别的硬约束，每条有 `C1`、`C2` 等稳定编号，
  并说明相互作用和省略后的失败后果。
- H2 `module_integration` 至少一个第二模块真正消费、写入、持久化或编排数据产物；纯列表、
  详情、概览、看板展示不算。
- H3 `design_tradeoff` 至少两个可行方案；每个方案必须通过 `preserves_constraint_ids`
  覆盖全部 H1 约束，并分别写清不同的 `correctness_effect` 与 `observable_result`。
- H3 必须填写 `decision_axis`、`trigger`、`both_options_valid`、
  `choice_changes_correctness`、`prompt_keeps_choice_open`、`fixed_branch_excluded`、
  `false_h3_guards` 和 `false_h3_counterexample`；题面只保留冲突和共同不变量，不预先
  规定“必须用新版本”“必须保留引用快照”“不能写回旧值”等分支胜负。
- 同一冲突轴不能在另一句预先固定。例如一句写“检查点冲突时以最新有效检查点为准”，
  另一句又让设计者决定“历史检查点和当前检查点谁优先”，平台会按 H3 不成立判废。
- H1/H2/H3 各自的 `prompt_excerpt` 必须逐字出现在最终题面；`module_anchors` 至少跨两个
  不同源码文件、两个模块且原文和行号可回查。
- `context_anchors` 至少两条，一条 `supports=trigger`，另一条支撑 `option_a` 或
  `option_b`；只指向 `STATUS_ORDER`、函数名或通用 CRUD 代码不算真实取舍依据。
- `anti_patterns` 的七项必须全为 `false`；`false_h3_guards` 的六项也必须全为 `false`。
  题面连续出现四个以上“先/再/逐项/依次”等过程词，同时没有开放判断或结果不变量时直接拒绝。

2026-11-15 `cc10010 / b1113-01` 的 8 条真实 `QC_PASSED` 样本已经证明：
“由你判断”“由你权衡后确定”“请自行选择”“优先级由你决定”“由你决定采用哪份”
都是可被平台识别的 H3 证据；而 14/35 两条 H1/H2 成立但 H3 被固定答案、兼容要求或
中断续做替代，最终 `DISCARDED`。2026-11-16 `dfzr10012` 又补充了

S11 新批次统一使用 `difficulty_contract_version: 3`，即使平台 G16 基础词面对普通类型只要求两项特征，
出题侧仍要逐题审计 H1/H2/H3 三项。词面已经出现“由你决定采用哪份”时，
`check_prompt_g16.py` 会记录正向校准，但 `difficulty_contract.py` 仍会检查两个方案、
结果不变量和同轴预先裁决。

### 5.1 跨项目全局防撞（2026-09-28 起跨目录硬闸）

这个闸门解决的是“单个项目内部已经不复读，但多个项目之间仍在套同一句骨架”：
`wx10001` 与 `wx10002` 的旧题面里，概览视图、批量作业、状态流转、规则阈值、导入导出、
权限归属、边界空态、列表筛选和持久一致性九组题都复用了同一开头、同一动作顺序和同一异常约束，
只把业务对象、页面名和字段名换掉。平台会把这判成跨项目相似并废弃，普通同仓库查重看不见。

执行口径：

- 出题前先同步当前 SOLO-QA 账号的平台题面快照。快照默认写到
  `data/platform-prompt-corpus.json`（该目录机器本地忽略，不提交），`update` 的跨项目
  检查会自动加载它，并用比提交侧更严的口径比较：相似度不低于 `13%`，或最长公共
  汉字片段达到 `30` 字即失败。
- 平台“雷同题库”已确认按关键词拒收的 `待办清单` 作为硬黑名单命中即拒写；平台明确
  说明该类换措辞无效，必须换真实业务场景。
- 跨项目范围以 `<父目录>/gsb-cross-project.json` 指向的注册表为准，不再要求所有批次在同一个
  父目录下。注册表里的每个工作簿路径都可以在不同目录树；注册表路径默认是
  `scripts/../data/cross-project-registry.json`，可用配置或 `GSB_CROSS_PROJECT_REGISTRY` 覆盖。
- `batch_prompt_workbook.py update` 检测到批次目录存在 `gsb-cross-project.json` 后，会自动读取
  注册表、加跨进程锁、执行跨项目检查；写表成功后把当前工作簿的路径、SHA-256、题面数量和更新时间
  原子写回注册表。注册表缺失、哈希不一致、题面数量不一致或覆盖不完整时直接拒写。
- 注册表模式下默认 `--require-coverage`：注册表里的工作簿必须存在且哈希匹配，当前批次至少要有
  1 条有题面的历史批次。零 peer 不是“通过”，只有显式 `--bootstrap-no-history` 才能放行首次批次；
  放行结果会写进生成清单。
- 出题前先扫描当前工作簿与全部已登记批次；每写一条题面前，`update` 内部会自动再查一次；
  整批写完后再全量复检一次。三次都必须在写表之前或写表后立即通过，不能等到投递后才发现。
- 命中近邻后，只改业务名词、页面名、同义词或标点不算重出。必须改至少两项：
  首屏形态（独立页 / 内嵌面板 / 日历 / 矩阵 / 时间轴 / 队列）、主交互对象、
  动作顺序、前后状态关系、异常反馈机制；同一 `任务类型 + 需求模式` 的解法形态不能照搬。
- `check_prompt_dedup.py` 只覆盖当前批次和历史记录，不能代替这个跨项目闸；
  `check_repo_theme.py` 只覆盖当前仓库的 topic × 模式，也不能代替。

#### raw A-5 公共长片段硬闸

A-5 不能只靠过滤后的业务文本和整题相似度判断。cc10011 的真实回执里，整题相似度只有
`7.56%—18.12%` 的题仍因不同 topic、不同任务类型复用同一段领域链而废弃；失败片段通常
跨越 `40—60` 个汉字。生成和写表时必须同时保留现有业务文本比较与独立的完整题面比较：

- raw 归一化只去除空白和中英文标点、统一大小写，不删除 H1/H2/H3，也不删除领域链、
  兼容、历史兼容、中断恢复、同步消费、另一业务面或跨模块句。
- 任一完整题面与 peer 的最长连续公共片段达到 `20` 字，直接失败。
- 同一题面内部重复出现达到 `20` 字的连续片段，直接失败。
- 两条完整题面存在任意完全相同的 `40` 字窗口，直接失败；这是平台等价硬闸。
- 与平台 `confirmed_a5_fragments` 完全一致，或连续公共片段覆盖 confirmed 片段的
  主体，直接失败。整题相似度低不是安全条件。
- 不为“兼容已有、兼容历史、中断后恢复、重复提交、状态单向推进、另一个业务模块、
  同步消费、数据快照、生成数据集”等词句设置全局白名单。真实已有接口名、字段名或
  固定协议名若必须保留，只能精确登记原文、原因和来源，并在结果中显示豁免来源，禁止
  正则或类别批量豁免。
- 写表闸门没有备注放行或 `--allow-gate-failure` 通道。`prompt-generation-manifest.json`
  必须记录 `raw_a5_ok / raw_a5_violation_count /
  raw_a5_max_common_fragment_length / raw_a5_max_internal_repeat_length /
  raw_a5_window_hits / raw_a5_nearest_pairs`，验收值为 `true / 0 / <=19 / <=19 / 0`。

#### domain_chain 与三段逐题句

1. 每个 `domain_chain` 只在主请求中完整表达一次。
2. 后续 H1、H2、H3 可以引用输入、产物和观察结果，但不得再次完整复述
   “读取输入 -> 处理 -> 生成产物 -> 保证可追溯”。
3. 禁止由全局数组按下标批量轮换“兼容已有……”“另一个业务入口……”
   “同步到协作业务面……”“中断后从上一完整数据继续……”等句子。
4. 每条题必须单独编写 `integration_sentence`、`implementation_constraint_sentence`
   和 `consumer_observation_sentence`，不能把这些字段当作批量模板换名词。
5. 上述三句必须写具体模块、具体数据产物和具体业务后果；只替换业务名词不算重写。
6. 同一 topic 的不同任务类型，不得复用完整 `domain_chain` 句子。
7. 不同 topic 之间也不得通过“兼容/同步/恢复/状态推进”模板形成 `20` 字以上公共片段。
8. 不需要在最终题面中追加通用的“验收观察”尾注；观察结果应自然落在具体业务主链路中。

固定命令：


`gsb-cross-project.json` 由建仓脚本在非 dry-run 建仓时自动写入；已有批次可手工补一份，或由
建仓脚本后续重跑时补写。首次批次确实没有任何历史时，把配置里的 `bootstrap_no_history` 临时设为
`true`，跑完首次建仓/生成后立即改回 `false`，并在生成清单里保留这次 bootstrap 记录。
S11 的 `update` 当前拒绝 `--allow-gate-failure`；备注、manifest 或历史字段都不能放行
raw A-5、跨项目注册表或其他硬闸。

脚本保留的过滤业务文本闸默认硬拦（先限定为同一任务类型且需求模式有交集，避免把不同模式
只共享行业词的题误伤）；raw A-5 闸不受这些条件限制：

- 字符三元组重合率 `> 20%`；
- 字符二元组余弦近似度 `> 35%`；
- 规范化开头公共前缀 `>= 12` 字；
- 两条题共享 `> 2` 个八字中文片段，或出现 `>= 20` 字连续中文片段；
- 解法形态重合并伴随三个以上业务能力点重合，或字符重合率超过 `16%`；
- 若任务类型或需求模式不相交，只在文字重合率 `> 60%`、语义近似度 `> 70%`，
  或连续中文片段达到 `40` 字时按极端克隆拦截。

输出必须带 `cross_project_ok`、`coverage_ok`、`registry_used`、`registry_path`、
`registry_batch_count`、`cross_project_violation_count`、
`cross_project_max_text_overlap`、`cross_project_max_semantic_similarity`、
`cross_project_max_common_fragment_length`、`cross_project_peer_batches`、`coverage_issues`、
`platform_guard_ok`、`platform_corpus_used`、`platform_corpus_path`、
`platform_dedup_ok`、`platform_dedup_violation_count`、`platform_dedup_max_similarity`、
`platform_dedup_max_common_fragment_length`、`platform_dedup_nearest`、
`platform_forbidden_topic_ok`、`platform_forbidden_topic_violations`、
`raw_a5_ok`、`raw_a5_violation_count`、`raw_a5_max_common_fragment_length`、
`raw_a5_max_internal_repeat_length`、`raw_a5_window_hits`、
`raw_a5_nearest_pairs` 和最近邻明细。
任一失败时不得写工作簿；按最近邻逐条写出“入口形态、动作顺序、状态关系、异常反馈”四个差异点后重出。
