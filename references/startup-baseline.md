## 3. 第一步：原始仓库启动预检与依赖基线

### 3.1 启动预检（所有路线的第一道硬闸）

GSB 的每个任务仓库都从同一个基准提交拉出，所以这份代码是整批任务的共同运行底座。
建仓前或已有任务目录进入生成前，必须真实启动一次并确认项目能正常运行；只看构建成功、
单元测试通过、静态检查通过或启动脚本存在，都不算通过。

启动对象必须是任务实际使用的基准提交，不能在带未提交改动的工作树上“顺手启动”后继续：

- 建仓前优先使用父目录里的原始代码目录。先记录 `git rev-parse HEAD`，并与计划用于 main
  的基准提交一致；`git status --porcelain` 非空时，改用一个从该提交拉出的干净持久工作树或
  干净克隆做预检，不要拿本地未提交改动冒充远端基准代码。推荐放在
  `<父目录>/.s11-dependency-seed/<源目录名>/`；这个目录是后续复制依赖的来源，预检结束后
  不得删除。
- `批量首轮路` 优先使用任意一个 `origin`（main 分支）做预检，并抽查各个 `origin` 的 HEAD
  都与基准提交一致、工作树无未提交改动；有脏改动时改用从该提交拉出的干净临时工作树做预检。
  若原始代码仓库仍在，再核对它的 `HEAD` / `git status`；源码目录缺失时不妨碍用任务克隆完成
  预检，但所有任务克隆必须指向同一个基准提交。
- 启动前先确认依赖安装口径和启动命令：读 `README` / `CONTRIBUTING`、`Makefile`、
  `package.json`、锁文件、`pyproject.toml` / `requirements*.txt`、`go.mod`、`Cargo.toml`、
  `docker-compose*.yml`、`.env.example` 等，优先执行项目文档声明的 `dev` / `start` / `serve` /
  `run` 命令，并按锁文件安装依赖。数据库、缓存、消息队列等项目启动必需组件也要一起拉起。
- Web / HTTP 服务必须等到真实监听后再判定：进程没有立即退出、预期端口处于监听状态、
  健康检查或文档给出的入口能收到响应，且启动日志没有致命错误。全栈项目要分别确认前端和
  后端关键进程都就绪，不能只确认其中一侧。
- CLI、worker、数据处理或库类项目没有 HTTP 服务时，必须运行文档声明的主入口或最小真实示例，
  确认能进入就绪状态或成功完成一次最小调用；仅执行编译、测试或 `--help` 不能替代启动预检。
- 默认端口被占用时顺延到可用端口，不要停掉别人的服务。预检启动的进程、子进程和
  `docker compose` 服务必须在检查结束后全部停掉；失败时也要清理，再返回阻塞原因。
  只清进程和临时运行状态，**不要删除这次安装出来的依赖目录**。禁止用
  `git clean -fdx` / `git clean -fdX`、`rm -rf node_modules`、删除 `.venv` 等方式“收尾”。

预检完成时记录并沿用以下证据：`startup_commit`、`startup_command`、`startup_result`、
就绪端口或入口、关键成功日志、`dependency_paths`、以及 `cleaned_up: true`。
批量建仓和生成阶段返回的 `startup_ok` 只有在这些信息齐全且启动对象与最终基准提交一致时
才能为 `true`。

任一项不满足就立即停止：

- 依赖安装失败、启动命令不存在、进程秒退、端口始终未监听、健康检查失败、
  启动日志出现致命错误，或必需组件无法连接，都按启动失败处理。
- 启动失败后不得继续建仓、整改、扫描工作簿、运行台账命令或写提示词，也不得改走
  `--allow-gate-failure` 绕过。给用户原样返回启动命令、基准提交、关键错误和缺失依赖，
  `blocking_reason` 以 `STARTUP_PREFLIGHT_FAILED:` 开头。
- 不要为了通过预检擅自修改原始仓库。用户修复源码后如果产生新的提交，旧任务仓库的
  `main` 已经不再等于新基准；必须先重新建仓或把main 分支与本地克隆对齐到
  新提交，再重新跑启动预检，不能继续在旧基线上出题。

同一轮批量任务只在源码、`base_commit`、启动命令或依赖发生变化时重新预检一次；
不得为了省这一步而省略，也不得用“之前某个任务启动过”代替当前基准提交的检查。

### 3.2 依赖目录保留、`.gitignore` 基线与启动复检

启动预检成功后，依赖目录就是后续所有任务的本地复用源，不得当作临时产物删除。先列出本次
启动实际生成、后续运行还需要复用的依赖根，至少按技术栈检查这些常见位置：

- Node：根目录和各个 workspace 下的 `node_modules/`；包管理器私有目录只有确认后续运行
  确实依赖时才保留。
- Python：`.venv/`、`venv/`、`env/`、`__pypackages__/`、`.tox/`、`.nox/` 等虚拟环境或
  已安装依赖目录。
- Ruby / PHP / Go 等：实际的 `vendor/bundle/`、`vendor/` 等依赖目录。若 `vendor/` 本来由
  Git 跟踪，不要把它当作可忽略依赖目录处理。
- Rust / Java / Gradle：`target/`、`.gradle/`、`build/` 等运行或构建依赖目录；只复制后续
  启动复用所需的部分，不复制日志、数据库、密钥、`.env`、业务数据或其他运行时污染。

确认依赖目录后，必须逐个用 `git check-ignore -v "<目录>"` 验证它们已经被原始仓库的
`.gitignore` 覆盖，而且不得出现在 `git status --porcelain` 的待提交列表里。

如果缺少忽略规则：

1. 只改原始仓库的 `.gitignore`，补上这些依赖目录的忽略模式，不把依赖目录本身加入 Git。
2. 只暂存 `.gitignore`，检查 `git diff --cached --name-only` 只有 `.gitignore`，然后提交。
3. 先把这条提交推送到原始仓库当前基准分支；推送成功并确认远端 SHA 后，这条新提交才是
   后续所有任务仓库的 `base_commit`。
4. 不要先建任务仓库再补 `.gitignore`，否则所有任务仓库都已经落在错误基线上。

如果原始仓库已经覆盖全部依赖目录，就不额外制造空提交，当前远端基准提交直接作为
`base_commit`。无论是否新增 `.gitignore` 提交，都要在当前基准提交上再启动或复检一次，
启动时保留依赖并确认没有重新安装；成功后只停服务，再记录最终 `startup_commit`。

依赖目录必须满足两个条件才允许复制：

- 目录已经被 `.gitignore` 覆盖，任务仓库里不会进入任何 main 产物提交。
- 目标运行环境能直接复用，至少在一个代表性任务克隆里做一次无安装启动 smoke。宿主与后续
  容器或目标机的 OS / CPU 不兼容，或 native 依赖不可重定位时，不能硬拷；只安装一次到
  代表性的任务运行环境，验证后再把这份可复用依赖复制给其余任务，仍需避免每个目录重复拉取。

最终基准提交必须是推送成功后的远端提交；`.gitignore` 提交不能只留在本地。
如果推送失败，立即停止，不建任务目录、不复制依赖、不生成题面。
