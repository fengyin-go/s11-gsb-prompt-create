## 核心判断

先写出题目唯一的主工作和可观察结果，再写题面：

1. **领域输入**：真实的数据对象从哪里进入，例如采集批次、原始日志、消息流、源表、上传文件、样本或历史存量。
2. **领域处理**：主体必须改变这些数据，例如采集、解析、清洗、转换、关联、去重、校验、聚合、入湖、落库、回填、归并、导出或计算指标。
3. **领域输出**：用户最终能检查什么数据结果，例如标准化数据集、明细表、质量报告、指标、水位、血缘关系、分区、导出文件或迁移后的存量。
4. **通用支撑**：权限、路由、灰度、发布、缓存、服务注册、UI、依赖锁和并发控制只能服务于上面的数据链路，不能成为题目的唯一主工作。

用一句话去掉产品名和页面名后复述主任务。若复述成“修服务状态机”“调路由权重”“做部署预检”“加权限配额”“升级构建工具”，本题就不是数据工程题。仅把对象名换成数据仓库术语仍不合格。

## domain_fit v2 硬契约

每个 `task_plan[].domain_fit` 必须使用以下结构。字段不是说明文字，而是建仓、写表、交接和运行侧都会冻结并校验的输入。

```json
{
  "version": 2,
  "main_task": "按采集批次解析原始日志并按批次去重，生成标准化明细数据集",
  "business_result": "标准化明细数据集可从来源批次和字段映射追溯到原始记录",
  "domain_chain": {
    "input": "采集批次中的原始日志",
    "operation": "解析原始日志",
    "output": "标准化明细数据集",
    "observable": "来源批次与字段映射可追溯"
  },
  "prompt_main_request": "请读取采集批次中的原始日志，解析原始日志并生成标准化明细数据集，保证来源批次与字段映射可追溯。",
  "genericization": {
    "rewritten_with_generic_objects": "维护一张带状态和权限的普通业务配置表",
    "same_task_without_domain_semantics": false
  },
  "source_evidence": ["backend/app/services/log_ingest.py"],
  "domain_anchors": [
    {
      "path": "backend/app/services/log_ingest.py",
      "start_line": 42,
      "end_line": 58,
      "supports": "operation",
      "excerpt": "按批次解析原始日志并写入标准化记录"
    },
    {
      "path": "backend/app/services/log_ingest.py",
      "start_line": 60,
      "end_line": 71,
      "supports": "output",
      "excerpt": "保存来源批次、字段映射和去重水位"
    }
  ],
  "conclusion": "pass"
}
```

约束：

- `domain_chain` 的 `input`、`operation`、`output`、`observable` 必须逐字出现在最终题面中。
- `prompt_main_request` 按任务类型自然起句，不要求以“请”开头；必须逐字出现在题面，并位于题面前 55% 或前 80 个字符以内，不能是末尾补的业务句。Bugfix 可先写真实故障现象，功能开发写能力缺口和新增目标，功能优化写现有链路与改进目标；重构和迁移分别写清不变行为、版本兼容目标。
- `main_task` 必须包含 `domain_chain.operation` 和 `output`，`business_result` 必须包含 `output`；计划字段与题面不能各说一套。
- `genericization` 必须写明去掉领域语义后会变成什么通用工程任务，且 `same_task_without_domain_semantics` 只能为 `false`。
- `domain_anchors` 至少两条真实源码锚点，行号、连续原文和 `supports` 必须与基准提交一致；至少一条锚定 `operation`，另一条锚定 `input` 或 `output`。
- `supports=operation` 的连续原文必须出现真实数据操作；`input/output` 锚点必须出现具体数据产物。只锚到函数名、路由或配置字段不算。
- `domain_anchors` 至少一条路径必须属于 `topic.evidence`。不能保留一个通用服务 topic，再从仓库别处借一段数据处理代码当锚点。
- `source_evidence` 必须包含锚点路径。路径存在但内容不涉及这条数据链，不能作为依据。
- 数据工程题必须在输入/输出、操作和可观察结果里分别命中真实数据产物或操作词；`observable` 不能只写“结果一致”。当前内置 profile 只做下限判断，语义主任务仍要逐题复核。

## 数据工程红线

2026-11-16 样稿反例：指标编号筛选未生效和 `/export` 被整数明细路由截获是真实 Bug，
但主修复是参数映射/路由可达性，并不能证明存在数据转换、聚合、去重或存储错误。
当前硬闸会拦截已知参数/路由主请求风险，其余情况仍须做语义审计；不能把正则未命中当作准入。
不能通过在该 Bugfix 后追加达成率计算、清洗或新数据集来补领域，因为这会改变任务类型。
简单除法与录入展示也不能仅凭“指标计算”四字自动成为困难数据工程题；需审计真实数据来源、
处理主体和结果语义，困难约束不能主要来自外围刷新状态或并发开关。

以下情况默认判为借壳，不进入容量、不建仓、不写表：

- 主任务是服务路由、负载均衡、限流、降级、网关配置、服务注册、实例健康或缓存键管理；数据只在验收末句被动出现。
- 主任务是权限归属、配额准入、鉴权、审批或越权拦截，没有数据采集、加工、存储或结果变化。
- 主任务是灰度发布、依赖锁、构建流水线、部署回滚、数据库版本对齐或配置管理。
- 主任务是普通状态机、并发 CAS、幂等回执或 UI 列表，即使模块名包含“数据”“血缘”“圈选”“湖仓”。
- 题面同时出现领域对象和领域结果，但这两个词只用于页面展示、录制或最后一句复述。
- `source_evidence` 只指向通用 CRUD router、前端页面、配置 schema 或服务治理脚本，没有真实数据处理代码。
- 把数据对象替换成商品、订单、用户、设备后，目标、约束、动作顺序和结果几乎不变。

数据语义为主体的前后端联动仍可合格，不要求每题只改后端，也不按修改文件数判断。关键在于主工作是否真的改变数据及其可追溯结果。

## 五类任务

五类题都检查主任务，不仅检查“依赖升级与迁移”：

- **功能开发**：新增真实数据能力，例如采集准入、字段解析、质量规则、增量归并、存量回填、导出或指标计算。
- **Bugfix**：修复真实的数据缺失、错算、错序、重复、口径不一致、水位倒退或回填中断；不要修通用服务状态机。
- **功能优化**：改善已有数据处理链路的吞吐、失败续做、去重、分区、查询或存储效率。
- **代码重构**：保持数据输入输出、口径和历史兼容不变，重构处理路径；不能只收拢服务判断。
- **依赖升级与迁移**：必须有真实数据格式、连接器、计算引擎或存储依赖目标，并验证存量与增量行为。缺目标时按 capacity-first 换题，不凑迁移比例。

## 三处强制检查

1. **排题位**：先写领域主工作和数据链，再建立 `domain_anchors`。语义不合格的题位不计容量、不建仓。
2. **写表**：`batch_prompt_workbook.py update` 会校验 v2 契约、源码锚点、主请求位置和领域词下限。命中红线时换主任务，不改领域字段、不追加业务词。
3. **交接**：`prepare_handoff.py` 再跑同一闸并冻结 v2 `domain_contract`。运行侧同时校验版本和新字段，禁止缺失后继续。

独立排错命令：

```bash
python3 <skill>/scripts/domain_fit.py \
  --parent "<batch目录>" \
  --repo "<任务目录>/origin"
```

平台之后给出新的领域判词时，先读取完整 `qc_checks` 和原题，归纳可泛化的主任务形状，再更新规则和回归样例；不要把单例扩成无证据的全面禁令。
